## 1 引言

### 1.1 编写目的

本文档定义"AI 驱动代码评审与测试生成平台"的完整功能需求、非功能需求、接口需求与数据需求，作为系统设计、开发、测试及验收的唯一依据。

### 1.2 项目背景

人工代码评审存在效率瓶颈、标准不一致、遗漏风险高等问题。本平台通过 Webhook 自动捕获代码变更，利用 LLM
进行多维度智能评审并生成测试用例，将评审意见与测试用例回写至代码托管平台，同时提供管理控制台供团队查看分析结果、配置评审规则与系统参数。

### 1.3 术语定义

| 术语         | 定义                                                                    |
|:-------------|:------------------------------------------------------------------------|
| MR/PR        | Merge Request / Pull Request，代码合并请求                              |
| Diff         | 代码变更差异                                                            |
| AST          | Abstract Syntax Tree，抽象语法树                                        |
| LLM          | Large Language Model，大语言模型                                        |
| Webhook      | 代码托管平台的事件回调机制                                              |
| RPC          | Remote Procedure Call，远程过程调用（本文指 HTTP+JSON 的 RPC 风格接口） |
| RBAC         | Role-Based Access Control，基于角色的访问控制                           |
| Idempotency  | 幂等性，同一请求多次执行产生的效果与执行一次相同                        |
| Diff Context | Diff 上下文，变更行前后的无关代码行，用于提供代码阅读上下文             |

## 2 总体描述

### 2.1 产品愿景

构建一站式 AI 代码质量守护平台，实现"代码提交 → 智能评审 → 测试生成 → 结果回写 → 质量度量"的全链路自动化闭环。

### 2.2 系统范围

**包含**：

- Webhook 事件接收与解析
- 代码 Diff 获取与 AST 上下文提取
- LLM 智能评审（需求分析 + 评审意见 + 测试用例，一次分析多路输出）
- 评审结果与测试用例回写至代码托管平台
- 管理控制台（评审概览、智能分析、规则配置、运维管理、权限管理、系统配置）

**不包含**：

- IDE 插件开发
- 代码静态分析引擎（依赖外部 SonarQube 等工具）
- CI/CD 流水线编排

### 2.3 用户角色

| 角色标识    | 角色名称   | 定位说明                                                       |
|:------------|:-----------|:---------------------------------------------------------------|
| `ADMIN`     | 系统管理员 | 拥有系统全部权限，负责平台接入、用户管理、系统运维             |
| `PM`        | 技术负责人 | 负责评审规则配置、团队数据查看、测试策略管理                   |
| `QA`        | 测试人员   | 审查 AI 生成的测试用例和评审意见，确认问题有效性，补充测试场景 |
| `DEVELOPER` | 普通开发者 | 查看自己相关的评审任务和报告，提交代码触发评审                 |
| `AUDITOR`   | 审计人员   | 可选，查看审计日志（菜单与数据权限见 7.3）                     |
| `OPERATOR`  | 运维人员   | 可选，查看任务、队列、模型调用（菜单与数据权限见 7.3）         |

### 2.4 运行环境

| 类别         | 要求                                                       |
|:-------------|:-----------------------------------------------------------|
| 服务端       | Linux（CentOS 7+ / Ubuntu 20.04+）                         |
| 数据库       | PostgreSQL 18+                                             |
| 缓存         | Redis 8.0+                                                 |
| 消息队列     | Kafka 4.3+                                                 |
| LLM          | 支持 OpenAI API 兼容协议（GPT-4o / DeepSeek / 通义千问等） |
| 浏览器       | Chrome 111+、Edge 111+、Firefox 128+、Safari 16.4+         |
| 代码托管平台 | GitLab 13+、GitHub、Gitea 1.16+                            |

### 2.5 设计约束

- API 统一采用 **RPC 风格**（POST + JSON Body），不使用 RESTful 风格
- 前端采用 Vue 3 + TypeScript + Vite+（`vp` CLI）+ Tailwind CSS v4，UI 组件层为 shadcn-vue（Reka UI）
- 后端采用 Spring Boot 4.1.x
- 所有 LLM 调用需支持超时降级与重试机制
- 测试用例生成模块设计为 **可插拔组件**，可独立关闭

### 2.6 假设与依赖

- 代码托管平台已开启 Webhook 功能且网络可达
- LLM 服务商 API 可用性 ≥ 99.5%
- 企业内部网络允许平台访问 LLM API 端点

### 3.2 智能分析

本模块是用户查看 AI 分析结果的核心区域，将需求分析、评审意见、测试用例三者统一呈现。

#### FR-005 任务列表

| 属性     | 说明                                                                                                   |
|:---------|:-------------------------------------------------------------------------------------------------------|
| 功能描述 | 以分页表格展示所有评审任务的历史记录                                                                   |
| 前置条件 | 用户已登录                                                                                             |
| 输入     | 筛选条件：仓库、作者、状态（待处理/已完成/失败等）、时间范围、关键字搜索                               |
| 输出     | 分页表格，字段包括：任务编号、仓库名称、MR/PR 标题、提交者、触发时间、状态、综合评分、是否包含测试用例 |
| 权限     | ADMIN / PM / QA 可查看全部；DEVELOPER 仅查看自己提交/参与的任务                                        |
| 业务规则 | 默认按触发时间倒序排列，每页 20 条                                                                     |

**状态清单**:

| 状态码          | 说明               |
|:----------------|:-------------------|
| RECEIVED        | 已接收             |
| PARSING         | 解析中             |
| QUEUED          | 排队中             |
| ANALYZING       | 分析中             |
| GENERATING_TEST | 测试生成中         |
| WRITING_BACK    | 回写中             |
| COMPLETED       | 已完成             |
| PARTIAL_SUCCESS | 部分成功           |
| FAILED          | 失败               |
| TIMEOUT         | 超时               |
| CANCELLED       | 已取消             |
| RETRYING        | 重试中             |
| DEGRADED        | 降级完成           |
| SKIPPED_QUOTA   | 已跳过（配额不足） |

> **状态体系说明**：本清单为任务业务状态的 **唯一口径**，共 14 个状态，持久化于 `review_task.sub_status`（见 6.1）；
> `review_task.status` 为主状态大类（0-待处理 / 1-处理中 / 2-已完成 / 3-失败 / 4-已取消），两者映射关系见 6.1
> 节"状态映射说明"。其中 `CANCELLED` 对应主状态码 **4**（BR-W-08 中"状态码 4"即指本状态），`SKIPPED_QUOTA` 由 BR-COST-03
> 配额熔断触发，主状态归入 **4-已取消**。

**状态流转规则**：

| 当前状态        | 触发事件               | 下一状态        | 说明                    |
|:----------------|:-----------------------|:----------------|:------------------------|
| RECEIVED        | 配额不足（BR-COST-03） | SKIPPED_QUOTA   | 跳过评审，MR 留言提示   |
| RECEIVED        | 开始解析               | PARSING         | 接收 Webhook 后开始解析 |
| PARSING         | 解析成功               | QUEUED          | 解析完成，等待调度      |
| PARSING         | 解析失败               | FAILED          | 记录错误码              |
| QUEUED          | 调度成功               | ANALYZING       | 开始 LLM 分析           |
| QUEUED          | 用户取消               | CANCELLED       | 排队中可取消            |
| ANALYZING       | 分析成功且需要生成测试 | GENERATING_TEST | 进入测试生成            |
| ANALYZING       | 分析成功且关闭测试生成 | WRITING_BACK    | 直接回写                |
| ANALYZING       | LLM 超时               | RETRYING        | 按策略重试              |
| ANALYZING       | 重试超限               | FAILED          | 终止任务                |
| ANALYZING       | LLM 不可用             | DEGRADED        | 降级完成                |
| ANALYZING       | 用户取消               | CANCELLED       | 分析中可取消            |
| RETRYING        | 重试成功               | ANALYZING       | 回到分析中              |
| RETRYING        | 重试失败               | FAILED          | 终止任务                |
| GENERATING_TEST | 生成成功               | WRITING_BACK    | 进入回写                |
| GENERATING_TEST | 生成失败               | PARTIAL_SUCCESS | 评审成功但测试生成失败  |
| GENERATING_TEST | 用户取消               | CANCELLED       | 测试生成中可取消        |
| WRITING_BACK    | 回写成功               | COMPLETED       | 任务完成                |
| WRITING_BACK    | 回写失败               | PARTIAL_SUCCESS | 分析成功但回写失败      |
| WRITING_BACK    | 超时                   | TIMEOUT         | 回写超时                |
| TIMEOUT         | 自动重试               | RETRYING        | 可配置                  |
| TIMEOUT         | 重试超限               | FAILED          | 终止任务                |
| PARTIAL_SUCCESS | 人工重试回写           | WRITING_BACK    | 重新回写                |
| DEGRADED        | 人工重试               | ANALYZING       | 重新分析                |

> **流转约束**：主状态层面遵循 BR-08 单向不可逆（0-待处理 → 1-处理中 → 2-已完成 / 3-失败 / 4-已取消）；业务状态层面仅允许上表中明确列出的三条
> **受控回退**（`TIMEOUT → RETRYING`、`PARTIAL_SUCCESS → WRITING_BACK`、`DEGRADED → ANALYZING`），回退须记录审计日志并累加重试次数；禁止主状态在
> 2/3/4 之间互转，禁止回退至 0-待处理。

| 属性     | 说明                                                      |
|:---------|:----------------------------------------------------------|

#### FR-007 变更追溯

| 属性     | 说明                                                                  |

### 3.3 规则配置

本模块供技术负责人统一管理评审规则和测试生成策略。

#### FR-008 指令管理

| 属性     | 说明                                                                                                                                |
|:---------|:------------------------------------------------------------------------------------------------------------------------------------|
| 功能描述 | 统一管理所有 LLM 提示词模板，支持变量引用、版本管理、效果评估                                                                       |
| 前置条件 | 用户已登录                                                                                                                          |
| 输入     | 指令名称、分类（系统指令/评审指令/测试生成指令/通用片段）、指令内容（支持变量占位符如 `{{diff_content}}`、`{{file_path}}`）、版本号 |
| 输出     | 指令列表（分页），支持按分类筛选                                                                                                    |
| 权限     | ADMIN：CRUD；PM：CRU（不可删除）；QA：只读；DEVELOPER：不可见                                                                       |
| 业务规则 | 每次修改自动保存历史版本；支持版本对比和回滚；支持引用其他 指令片段（{{ref:片段名}}）                                               |

**核心功能点**：

| 功能       | 说明                                                                                          |
|:-----------|:----------------------------------------------------------------------------------------------|
| 变量占位符 | 支持 `{{diff_content}}`、`{{file_path}}`、`{{language}}`、`{{rule_description}}` 等运行时变量 |
| 指令组合   | 支持引用其他 指令片段，如评审指令中引用通用输出格式片段：`{{ref:output_format_v2}}`           |
| 版本管理   | 每次修改自动保存历史版本，支持版本对比和回滚                                                  |
| 效果评估   | 可关联历史评审任务，对比不同 指令版本产出的评审意见质量（确认率/误报率）                      |
| 分类管理   | 分为系统指令（全局角色设定）、评审指令（各维度评审）、测试生成指令、通用片段四类              |

**与现有模块的关系**

- 指令管理（统一管理 指令模板）→ 引用 → 评审规则（每条规则引用一个评审指令 Prompt）
- 指令管理 → 引用 → 测试策略（引用一个测试生成指令 Prompt）
- 指令管理 → 引用 → 智能分析引擎（运行时组装最终 Prompt：系统指令 + 评审指令/测试指令 + 变量填充）与现有模块的关系

#### FR-009 评审规则

| 属性     | 说明                                                                                                                        |
|:---------|:----------------------------------------------------------------------------------------------------------------------------|
| 功能描述 | 管理代码审查规则                                                                                                            |
| 输入     | 规则编号、规则名称、所属维度（Bug/性能/安全/风格/可读性）、规则描述、严重等级（Blocker/Critical/Minor）、启用状态、指令模板 |
| 输出     | 规则列表（分页）                                                                                                            |
| 权限     | ADMIN：CRUD；PM：CRUD；QA：只读；DEVELOPER：只读                                                                            |
| 业务规则 | 系统内置规则不可删除，仅可修改描述和启用状态；                                                                              |
|          | 每条规则关联一个 指令模板（通过 FR-008 管理）；                                                                             |
|          | 规则表以 `prompt_template`（TEXT）去规范化存储模板内容快照，非外键引用，与 `test_strategy` 设计一致                         |

#### FR-010 测试策略

| 属性     | 说明                                                                                                             |
|:---------|:-----------------------------------------------------------------------------------------------------------------|
| 功能描述 | 管理测试用例生成策略                                                                                             |

| 业务规则 | 每个仓库可绑定一个测试策略，未绑定则使用全局默认策略；QA 提出的修改建议需 PM 审批后生效                          |

### 3.4 运维管理

本模块供系统管理员进行系统运维和安全审计。

#### FR-012 系统监控

### 3.7 核心引擎功能

#### FR-022 Webhook 接收与解析

| 属性     | 说明                                                                                                                    |
|:---------|:------------------------------------------------------------------------------------------------------------------------|
| 功能描述 | 接收代码托管平台的 Webhook 事件，解析 MR/PR 的创建/更新事件                                                             |
| 输入     | Webhook 请求体（JSON）                                                                                                  |
| 输出     | 评审任务记录（状态：待处理）                                                                                            |
| 权限     | 无需认证（由代码托管平台回调）                                                                                          |
| 业务规则 | 校验 Webhook Secret 签名；过滤非 MR/PR 事件；去重（同一 MR 短时间内多次触发只处理最新一次）；将任务写入消息队列异步处理 |

**支持的事件类型**

| 平台   | 事件类型                            | 触发时机             | 处理策略               |
|:-------|:------------------------------------|:---------------------|:-----------------------|
| GitLab | merge_request (action: open)        | MR 创建              | 创建评审任务           |
| GitLab | merge_request (action: update)      | MR 有新提交/描述更新 | 取消旧任务，创建新任务 |
| GitLab | merge_request (action: merge)       | MR 合并              | 忽略，不触发评审       |
| GitLab | merge_request (action: close)       | MR 关闭              | 取消待处理任务         |
| GitHub | pull_request (action: opened)       | PR 创建              | 创建评审任务           |
| GitHub | pull_request (action: synchronize)  | PR 有新提交          | 取消旧任务，创建新任务 |
| GitHub | pull_request (action: closed)       | PR 关闭/合并         | 取消待处理任务         |
| Gitea  | pull_request (action: opened)       | PR 创建              | 创建评审任务           |
| Gitea  | pull_request (action: synchronized) | PR 有新提交          | 取消旧任务，创建新任务 |
| Gitea  | pull_request (action: closed)       | PR 关闭/合并         | 取消待处理任务         |

**业务规则**

| 规则编号 | 规则名称            | 规则描述                                                                                                                                                                                                                                                                                                                      |
|:---------|:--------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| BR-W-01  | 事件过滤            | 仅处理上表中标注为"创建评审任务"和"取消旧任务，创建新任务"的事件；未列出的事件类型直接返回 HTTP 200 并忽略，**仅落计数指标与 DEBUG 级摘要（事件类型、来源 IP），不记录 Payload 正文**；MR/PR 合并（merge）事件不触发评审                                                                                                      |
| BR-W-02  | 快速响应原则        | 接口必须在 200ms 内完成接收、校验并入队，严禁在接口线程中执行 Diff 解析或 LLM 调用                                                                                                                                                                                                                                            |
| BR-W-03  | 签名验证 - GitLab   | 从请求头 X-Gitlab-Token 中取出 Token，与配置的 Webhook Secret 直接比对；不匹配则返回 HTTP 401                                                                                                                                                                                                                                 |
| BR-W-04  | 签名验证 - GitHub   | 从请求头 X-Hub-Signature-256 中取出签名，使用 HMAC-SHA256 对请求 Body 计算签名后比对；不匹配则返回 HTTP 401                                                                                                                                                                                                                   |
| BR-W-05  | 签名验证 - Gitea    | 从请求头 X-Gitea-Signature 中取出签名，使用 HMAC-SHA256 对请求 Body 计算签名后比对；不匹配则返回 HTTP 401                                                                                                                                                                                                                     |
| BR-W-06  | 签名失败处理        | 签名验证失败时返回 HTTP 401，不记录请求 Body（防止恶意 payload 污染日志），仅落审计日志（来源 IP、时间戳、失败原因）；**与之相对，签名通过的目标事件**按《LLD》§8.2 记录脱敏后的 Payload 摘要；连续 5 次签名验证失败的 IP 自动加入临时黑名单（封禁 30 分钟）；未配置 Webhook Secret 的平台实例跳过签名验证（仅开发/测试环境） |
| BR-W-07  | 幂等去重 - 事件 ID  | 利用 X-Gitlab-Event-UUID（GitLab）或 X-GitHub-Delivery（GitHub）作为幂等键（**Gitea 平台的事件级幂等键本期不实现，列入二期**；Gitea 侧本期由 BR-W-08 的业务去重 Key 兜底）；查询 Redis 判断是否已处理过；已存在的直接返回 200 OK 并不再创建新任务；幂等 Key 在 Redis 中缓存 24 小时                                           |
| BR-W-08  | 幂等去重 - 任务状态 | 以 {平台实例ID}_{仓库ID}_{MR_ID} 作为业务去重 Key；窗口内（60 秒）旧任务标记为"已取消"（状态码 4），创建新任务；若旧任务已进入"处理中"状态，则不取消旧任务，直接丢弃新请求，避免中断正在进行的 LLM 调用；去重窗口内旧任务取消操作与新任务创建操作必须在同一事务中完成                                                         |
| BR-W-09  | HTTP 状态码规范     | 校验通过（含重复请求）返回 HTTP 200；签名验证失败返回 HTTP 401；参数错误返回 HTTP 400；系统过载（MQ 满）返回 HTTP 503（触发平台重试）；非目标事件返回 HTTP 200（避免平台误报重试）                                                                                                                                            |
| BR-W-10  | 异步解耦            | 任务入队后由后台 Worker 消费消息进行 Diff 获取和分析；若 Worker 处理失败通过 MQ 的重试机制处理，不依赖 Webhook 的 HTTP 重试                                                                                                                                                                                                   |

**Webhook 响应策略**

| 场景       | HTTP 状态码             | 响应 Body 示例                                                                                        | 平台行为 | 说明                     |
|:-----------|:------------------------|:------------------------------------------------------------------------------------------------------|:---------|:-------------------------|
| 处理成功   | 200 OK                  | {"code":0,"message":"success","data":{"status":"accepted","taskId":123},"requestId":"uuid"}           | 停止重试 | 校验通过，任务已入队     |
| 签名错误   | 401 Unauthorized        | {"code":40301,"message":"invalid signature","data":null,"requestId":"uuid"}                           | 停止重试 | 安全拦截，不需要平台重试 |
| 非目标事件 | 200 OK                  | {"code":0,"message":"success","data":{"status":"ignored","reason":"not mr event"},"requestId":"uuid"} | 停止重试 | 如 Push 事件，直接忽略   |
| 重复请求   | 200 OK                  | {"code":0,"message":"success","data":{"status":"duplicate","existTaskId":123},"requestId":"uuid"}     | 停止重试 | 幂等性拦截               |
| 参数错误   | 400 Bad Request         | {"code":40001,"message":"invalid payload","data":null,"requestId":"uuid"}                             | 停止重试 | 数据格式不对，重试无效   |
| 系统繁忙   | 503 Service Unavailable | {"code":50001,"message":"queue full","data":null,"requestId":"uuid"}                                  | 触发重试 | MQ 满了或系统过载        |

| 属性     | 说明                                                                    |
|:---------|:------------------------------------------------------------------------|

**硬性阈值拦截（第一道防线）**

| 阈值类型           | 建议值    | 处理策略                                                                   |
|:-------------------|:----------|:---------------------------------------------------------------------------|
| 单文件行数         | > 1000 行 | 标记为"超大文件"，跳过评审，直接生成一条 Comment："文件变更过大，建议拆分" |
| 单次 MR 总变更行数 | > 2000 行 | 触发"精简模式"，仅评审变更最密集的前 10 个文件（N 默认 10）                |
| 文件数量           | > 20 个   | 触发"目录级评审"，只分析目录结构和文件名变更，不深入代码行                 |
| Payload 大小       | > 5MB     | 直接拒绝 Webhook 请求（HTTP 413），提示"变更内容过大"                      |

**智能精简策略**

| 策略           | 规则                                                                                                                                                                                                                    |
|:---------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 上下文裁剪     | 默认保留变更行前后各 3-5 行上下文；对于非连续变更（中间隔了 100 行空行），自动折叠中间无关代码，只保留变更块                                                                                                            |
| 非代码内容过滤 | 自动识别并过滤以下内容的变更（除非用户强制开启）：第三方库文件（node_modules、vendor、lib）、生成的代码（*.pb.go、*.min.js、dist/）、纯配置文件变更（package-lock.json、yarn.lock，除非涉及安全漏洞）、图片/Binary 文件 |
| 语言识别       | 如果 Diff 中包含超过 5 种编程语言，优先评审主语言（根据 pom.xml / package.json 推断），忽略次要语言（如文档、脚本）                                                                                                     |

**降级处理模式**

> **判定对象**：下表触发条件中的 Token 指 **单次评审任务的输入 Token 估算值（整任务口径）**，估算方法见《Prompt（指令）设计说明书》§5.2；三个 LLM 阶段共享同一判定结果，不按单阶段预算重复判定。整任务的 Token 预算遵循 BR-04（默认 8000，含阶段一额度）。

| 模式     | 触发条件        | 行为描述                                                                  |
|:---------|:----------------|:--------------------------------------------------------------------------|
| 标准模式 | Token < 4k      | 全量分析：变更意图 + 详细评审 + 测试用例生成                              |
| 精简模式 | 4k ≤ Token ≤ 8k | 只保留变更意图分析 + 关键逻辑评审。跳过风格检查，不生成测试用例           |
| 速览模式 | Token > 8k      | 仅做安全检查。只扫描明显的 SQL 注入、硬编码密码、空指针风险。忽略业务逻辑 |
| 分片模式 | 单文件极大      | 将大文件切分为多个 Chunk 并行评审，最后合并结果（建议二期实现）           |

#### FR-026 反馈闭环与模型优化

| 属性     | 说明                                                                                                |
|:---------|:----------------------------------------------------------------------------------------------------|
| 功能描述 | 收集用户对 AI 评审意见的反馈（确认/误报），利用反馈数据优化后续评审质量，形成"使用-反馈-优化"闭环。 |
| 前置条件 | 用户已对评审意见执行"确认有效"或"标记误报"操作。                                                    |
| 输入     | 反馈数据（任务ID、文件路径、代码行、原始 Prompt、AI 输出、用户操作类型）。                          |
| 输出     | 优化后的 指令上下文、误报特征库更新。                                                               |
| 权限     | 后台自动执行，ADMIN 可查看优化报告。                                                                |

**业务规则**

| 规则编号 | 规则名称       | 规则描述                                                                                                                                                                                            |
|:---------|:---------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| BR-FB-01 | 误报特征库     | 当 QA/开发者标记"误报"时，系统提取该代码片段的 AST 特征和语义向量，存入"误报特征库"。                                                                                                               |
| BR-FB-02 | 动态上下文注入 | 在下一次评审任务生成 指令时，系统检索当前代码与"误报特征库"的相似度。若相似度 > 85%，则在 System 指令中注入负面约束示例："注意：类似的代码模式在历史记录中被标记为误报，请勿针对此类情况提出建议。" |
| BR-FB-03 | 确认样本库     | 当用户标记"确认有效"且开发者随后提交了修复代码，系统将该（问题代码 -> 修复代码）对存入"高质量修复样本库"，用于 Few-shot 示例的随机抽取。                                                            |
| BR-FB-04 | 效果评估报表   | 系统每周生成"模型效果周报"，展示误报率下降趋势、指令优化次数及用户采纳率。                                                                                                                          |

**要求**：

1. 行级评论统一使用 **新文件 1-indexed 行号**，与评审意见中的行号一致（FR-006 / FR-024）。

#### 5.3.2 LLM 出站接口

| 项         | 要求                                                                                |

> 2. `TIMEOUT` 归入"处理中"，因其可自动重试至 RETRYING，超限后转 FAILED。
> 3. `PARTIAL_SUCCESS`、`DEGRADED` 归入"已完成"，因主体评审结果已产出且允许人工重试激活。
> 4. `CANCELLED` 对应 BR-W-08 中的"状态码 4"；`SKIPPED_QUOTA` 由 BR-COST-03 配额熔断触发，同属主状态 4。

| 字段          | 类型          | 约束                                 | 说明                                     |
|:--------------|:--------------|:-------------------------------------|:-----------------------------------------|
| id            | BIGINT        | PK, GENERATED BY DEFAULT AS IDENTITY | 主键                                     |
| subject_type  | VARCHAR(16)   | NOT NULL                             | 主体类型：DEPT/PROJECT                   |
| subject_id    | BIGINT        | NOT NULL                             | 主体 ID（部门 ID 或项目 ID）             |
| model_id      | BIGINT        | FK                                   | 关联模型配置 ID（`model_config`）        |
| stat_date     | DATE          | NOT NULL                             | 统计日期（支撑"当日消耗"，BR-COST-01）   |
| stat_month    | VARCHAR(7)    | NOT NULL                             | 统计月份，格式 YYYY-MM（支撑"当月消耗"） |
| input_tokens  | BIGINT        | DEFAULT 0                            | 输入 Token 累计                          |
| output_tokens | BIGINT        | DEFAULT 0                            | 输出 Token 累计                          |
| total_tokens  | BIGINT        | DEFAULT 0                            | 总 Token 累计                            |
| amount        | NUMERIC(12,2) | DEFAULT 0                            | 消耗金额（按模型单价计算，BR-COST-01）   |
| created_at    | TIMESTAMPTZ   | NOT NULL                             | 创建时间                                 |
| updated_at    | TIMESTAMPTZ   | NOT NULL                             | 更新时间                                 |

> 说明：
> 1. 配额状态（是否达 80%/90% 告警阈值、是否 100% 熔断）由 `cost_quota` 与 `cost_consumption` 实时计算得出，经
     `/api/v1/cost/quotaStatus` 返回，不单独落库。
> 2. 达到 100% 配额时按 BR-COST-03 暂停该主体范围内 AI 评审，任务业务状态置 `SKIPPED_QUOTA`（主状态 4-已取消）。
> 3. 模型单价取自 `model_config.input_price` / `output_price`（每千 Token），为 FR-021 前置条件"系统已配置 LLM
     模型及单价（或在模型配置中预设）"的落地。
