## 1 项目背景与目标

### 1.1 项目背景

人工代码评审存在 **效率瓶颈、标准不一致、遗漏风险高**等问题。本平台通过 **Webhook 自动捕获代码变更**，利用 **LLM
进行多维度智能评审并生成测试用例**，将评审意见与测试用例 **回写至代码托管平台**，同时提供 **管理控制台**
供团队查看分析结果、配置评审规则与系统参数。

### 1.2 编写目的

SRS 定义本平台的完整功能需求、非功能需求、接口需求与数据需求，作为系统设计、开发、测试及验收的唯一依据。本概要设计说明书在 SRS
基础上，对系统的总体架构、模块划分、核心流程、数据/接口设计、非功能需求与部署环境进行归纳与结构化，作为后续详细设计与实现的输入。

### 1.3 产品愿景与目标

构建 **一站式 AI 代码质量守护平台**，实现"**代码提交 → 智能评审 → 测试生成 → 结果回写 → 质量度量**"的全链路自动化闭环。

### 1.4 系统范围

**包含**：

- Webhook 事件接收与解析
- 代码 Diff 获取与 AST 上下文提取
- LLM 智能评审（需求分析 + 评审意见 + 测试用例，一次分析多路输出）
- 评审结果与测试用例回写至代码托管平台
- 管理控制台（评审概览、智能分析、规则配置、运维管理、权限管理、系统配置）

**不包含**：

- IDE 插件开发
- 代码静态分析引擎（依赖外部 SonarQube 等工具）
- CI/CD 流水线编排

### 1.5 用户角色

| 角色标识    | 角色名称   | 定位说明                                                       |
|:------------|:-----------|:---------------------------------------------------------------|
| `ADMIN`     | 系统管理员 | 拥有系统全部权限，负责平台接入、用户管理、系统运维             |
| `PM`        | 技术负责人 | 负责评审规则配置、团队数据查看、测试策略管理                   |
| `QA`        | 测试人员   | 审查 AI 生成的测试用例和评审意见，确认问题有效性，补充测试场景 |
| `DEVELOPER` | 普通开发者 | 查看自己相关的评审任务和报告，提交代码触发评审                 |
| `AUDITOR`   | 审计人员   | 可选，查看审计日志（菜单与数据权限见 SRS 7.3）                 |
| `OPERATOR`  | 运维人员   | 可选，查看任务、队列、模型调用（菜单与数据权限见 SRS 7.3）     |

## 2 系统总体架构

### 2.1 设计约束（来自 SRS 2.5）

- **API 风格**：统一采用 **RPC 风格**（`POST + JSON Body`），不使用 RESTful 风格。
- **前端技术栈**：Vue 3 + TypeScript + Vite+（`vp` CLI）+ Tailwind CSS v4 + shadcn-vue(Reka UI)。
- **后端技术栈**：Spring Boot 4.1.x。
- **LLM 调用**：所有 LLM 调用需支持 **超时降级与重试机制**。
- **可插拔设计**：测试用例生成模块设计为 **可插拔组件**，可独立关闭。

### 2.2 逻辑架构分层

### 2.3 关键架构设计要点

| 设计点           | 设计方式（依据 SRS）                                                                         |
|:-----------------|:---------------------------------------------------------------------------------------------|
| 异步解耦         | Webhook 入队后由后台 Worker 消费消息进行 Diff 获取与分析；MQ 重试不依赖 HTTP 重试（BR-W-10） |
| 无状态服务       | 支持多实例部署 + 负载均衡（4.5 水平扩展）                                                    |
| 平台可扩展       | Webhook 解析层采用**策略模式**，新增平台只需实现适配接口（4.5）                              |
| LLM 可扩展       | 模型调用层采用**适配器模式**，新增提供商只需实现适配接口（4.5）                              |
| 评审维度可扩展   | 评审规则支持自定义维度，无需修改核心代码（4.5）                                              |
| 一次分析多路输出 | 阶段一变更意图分析 → 阶段二评审意见 + 阶段三测试用例并行（BR-01~BR-03）                      |
| 可插拔测试生成   | 测试用例生成模块可独立关闭，关闭后跳过阶段三（BR-10）                                        |

### 2.4 工程模块（物理架构）与依赖约束

#### 2.4.1 定位与术语区分

本章将 §2.2 的逻辑分层映射为具体的 Maven 多模块工程结构，作为编码实现与 CI/CD 的物理依据。整体为**单体模块化架构**：同一代码库、多个可执行入口（web/webhook/worker），各入口按需装配库模块并独立部署、独立扩容，不引入注册中心/服务网关。

> **术语区分**：本章"模块"特指 **Maven 工程模块**（`aicr-*`）；与 §3 所述"功能模块"（评审概览/智能分析/规则配置等 7 大业务域）为不同维度。功能模块在物理工程中体现为 Maven 模块内的**包（package）**，而非独立 Maven 模块。

#### 2.4.2 模块清单与职责边界

系统为技术分层型多模块（父 `pom` 仅做聚合与版本管理），含 6 个库模块 + 3 个可执行模块，共 9 个：

| 模块            | 类型                     | 职责边界                                                                                         | 禁止事项                                                      |
|:----------------|:-------------------------|:-------------------------------------------------------------------------------------------------|:--------------------------------------------------------------|
| `aicr-common`   | 库（基础工具包）         | 所有模块共享的常量、枚举、通用返回结果、工具类                                                   | 禁止引入 Spring / Web / 任何业务依赖                          |
| `aicr-api`      | 库（契约定义包）         | 对外 RPC 接口 DTO、`*Action` 请求/响应体、内部调用接口声明（单体下为进程内接口，非跨网络 Feign） | 禁止包含 Controller/Service 实现与业务逻辑                    |
| `aicr-security` | 库（安全核心包）         | 认证、授权、加密（AES-256）、脱敏逻辑；定义 `UserDetailsLoader`/`DataScopeResolver` SPI          | 禁止包含用户/角色/权限 CRUD（实现归属 `service`）             |
| `aicr-base`     | 库（基础设施层）         | 数据持久化（Repository/Mapper）、消息队列（Kafka 生产/消费封装）、全局配置、全局异常处理         | 禁止编写业务逻辑；禁止依赖业务模块                            |
| `aicr-service`  | 库（业务逻辑层）         | 核心业务功能（评审/规则/用户管理等），调用 `base` 操作数据，实现 `api` 内部接口                  | 禁止直接 `new`/`调用 engine 内部类`触发分析（触发走 Kafka）   |
| `aicr-engine`   | 库（后台引擎层）         | 异步耗时后台任务：智能分析、结果回写、大变更策略、反馈闭环（FR-022~026）                         | **禁止依赖 `service`**（经 `base` 读写，经 `api` 接口调用）   |
| `aicr-web`      | 可执行 jar（前台应用层） | 管理控制台 API 控制器，处理用户请求，调用 `service`                                              | 禁止装配/依赖 `engine`；禁止承载 Kafka 消费                   |
| `aicr-webhook`  | 可执行 jar（回调服务层） | 处理 Git 平台 Webhook 回调（签名校验+幂等+建任务+入队），独立部署                                | **禁止依赖 `service`/`engine`**（仅 `base`+`security`+`api`） |
| `aicr-worker`   | 可执行 jar（引擎执行层） | Kafka 消费入口，装配并驱动 `engine` 执行（与 §8.2 一致）                                         | 禁止暴露 Web 控制器；除驱动 engine 外不写业务                 |

#### 2.4.3 依赖方向原则

遵循**单向无环、底层不反向依赖上层**：

1. 库依赖链：`{service, engine} → {base, security, api} → common`；`web/webhook/worker` 为装配层，可依赖所需库。
2. **红线一（解环关键）**：`engine` 与 `webhook` **禁止依赖 `service`**。二者数据访问由 `base` 的 Repository 提供，所需配置/计费/通知经 `api` 内部接口由 `service` 在同一进程内实现，彻底规避 `engine↔service` 循环依赖。
3. **红线二**：`web` **禁止依赖 `engine`**。`web` 仅经 `service` 发送 Kafka 消息（`review/trigger`、`review/retry`、`webhook/retry`）；`engine` 的唯一执行入口是 `worker`。契合 BR-W-10「MQ 重试不依赖 HTTP 重试」。
4. **红线三**：`common` 零框架依赖，任何模块可依赖它，它不得依赖任何业务模块。
5. `security` 仅以 SPI/库形式存在，用户/权限数据加载实现在 `service`，避免 `security↔service` 反向依赖。

#### 2.4.4 依赖矩阵

`→` 表示允许依赖；空白表示禁止。

| 依赖方 ↓ / 被依赖方 → | common | api | base | security | service | engine |
|:----------------------|:------:|:---:|:----:|:--------:|:-------:|:------:|
| api                   |   →    |     |      |          |         |        |
| base                  |   →    |  →  |      |          |         |        |
| security              |   →    |  →  |  →   |          |         |        |
| service               |   →    |  →  |  →   |    →     |         |        |
| engine                |   →    |  →  |  →   |    →     | **禁**  |        |
| web                   |   →    |  →  |  →   |    →     |    →    | **禁** |
| webhook               |   →    |  →  |  →   |    →     | **禁**  | **禁** |
| worker                |   →    |  →  |  →   |    →     |    →    |   →    |

> 注：`worker` 装配 `service`+`engine` 仅为在同一进程内提供 engine 所需的内部能力（计费/通知/配置实现），`engine` 模块本身仍不依赖 `service`（红线一不变）。

#### 2.4.5 架构约束固化

- **Maven Enforcer**：`bannedDependencies` 显式禁止 `engine → service`、`web → engine`、`webhook → {service, engine}`、`common → spring-*`。
- **ArchUnit 分层测试**（进 CI）：以 `layeredArchitecture()` 校验 §2.4.4 矩阵，任一违反构建失败。
- 父 `pom` 仅聚合 + `dependencyManagement`；仅 `web`/`webhook`/`worker` 允许 `spring-boot-maven-plugin` repackage，库模块禁止。

#### 2.4.6 部署单元

| 部署单元       | 装配模块                                | 扩容依据           | 关键 SLA                         |
|:---------------|:----------------------------------------|:-------------------|:---------------------------------|
| `aicr-web`     | service+security+api+base+common        | 在线用户数 / QPS   | 首屏 ≤2s，API P99 ≤2s（LLD 9.1） |
| `aicr-webhook` | base+security+api+common                | Webhook QPS（≥50） | P99 ≤200ms（HLD 7.1）            |
| `aicr-worker`  | engine+service+base+security+api+common | Kafka 消费 lag     | 单任务 ≤5min（LLD 9.1）          |

三个单元共享同一 PostgreSQL / Redis / Kafka；Flyway/Liquibase 迁移须仅由单一单元（建议 `worker` 启动或独立 migration Job）执行，避免多实例并发上锁。

#### 2.4.7 演进项

- **`base` 职责偏重**：同时承载持久化 + Kafka + 全局配置 + 异常处理，易膨胀。二期建议拆为 `aicr-data`（Repository）、`aicr-mq`（Kafka）、`aicr-framework`（配置/异常）三库。
- **出站集成层**：LLM 适配器/代码平台客户端/通知渠道当前置于 `engine`，若需被 `service` 复用（平台连通性测试 FR-018、配额告警 FR-021），二期应抽 `aicr-integration` 模块由二者共同依赖。

### 3.2 模块功能说明

- **评审概览模块**：宏观展示团队代码质量状况（指标卡片、问题分布、质量趋势、仓库分析）。
- **智能分析模块**：用户查看 AI 分析结果的核心区域，统一呈现需求分析、评审意见、测试用例，并提供变更追溯图谱。
- **规则配置模块**：统一管理 LLM 指令模板、评审规则、测试生成策略与规则模板，指令模板被评审规则、测试策略、智能分析引擎引用。
- **运维管理模块**：系统运行时指标监控（QPS、延迟、成功率、Token 消耗、队列积压）与审计日志查询。
- **权限管理模块**：基于 RBAC 的用户、角色、部门与数据权限管理（菜单权限 + 数据权限独立）。
- **系统配置模块**：全局接入配置，包括代码托管平台接入、LLM 模型配置、通知设置与成本管理（配额/熔断）。
- **核心引擎模块**：平台后台自动执行的能力，承载 Webhook 接收、LLM 智能分析、结果回写、大变更降级处理与反馈优化闭环。

## 4 核心业务流程

### 4.1 主业务流程：代码提交到结果回写

```
开发者提交 MR/PR
      │
      ▼
[Webhook 接收与解析 FR-022]
  · 校验 Webhook Secret 签名（GitLab/GitHub/Gitea 各平台策略）
  · 过滤非 MR/PR 事件，幂等去重（事件ID + 任务状态）
  · 200ms 内完成接收/校验/入队（BR-W-02），不在此线程执行解析
      │  入 Kafka 队列
      ▼
[后台 Worker 消费]
  · 获取代码 Diff 与 AST 上下文
  · 大变更处理策略 FR-025（阈值拦截/智能精简/降级模式）
      │
      ▼
[智能分析引擎 FR-023 — 一次分析多路输出]
  阶段一：变更意图分析
      ├─ 阶段二：评审意见生成 ┐
      └─ 阶段三：测试用例生成 ┘（阶段二、三并行，BR-03）
  上下文共享（阶段一输出作为阶段二/三 System 指令输入，BR-02）
      │
      ▼
[结果回写 FR-024]
  · Inline Comment（行级）+ Summary Comment（汇总）
  · 回写失败标记 PARTIAL_SUCCESS，支持人工重试
      │
      ▼
[质量度量] → 评审概览指标更新 + 反馈闭环（FR-026）
```

### 4.2 任务状态流转（来自 SRS 3.1，唯一口径共 14 个业务状态）

**主状态（`review_task.status`）**：0-待处理 / 1-处理中 / 2-已完成 / 3-失败 / 4-已取消（单向不可逆，BR-08）。

**业务状态（`review_task.sub_status`）** 及关键流转：

| 当前状态        | 触发事件               | 下一状态        |
|:----------------|:-----------------------|:----------------|
| RECEIVED        | 配额不足（BR-COST-03） | SKIPPED_QUOTA   |
| RECEIVED        | 开始解析               | PARSING         |
| PARSING         | 解析成功               | QUEUED          |
| PARSING         | 解析失败               | FAILED          |
| QUEUED          | 调度成功               | ANALYZING       |
| QUEUED          | 用户取消               | CANCELLED       |
| ANALYZING       | 分析成功且需生成测试   | GENERATING_TEST |
| ANALYZING       | 分析成功且关闭测试生成 | WRITING_BACK    |
| ANALYZING       | LLM 超时               | RETRYING        |
| ANALYZING       | 重试超限               | FAILED          |
| ANALYZING       | LLM 不可用             | DEGRADED        |
| ANALYZING       | 用户取消               | CANCELLED       |
| RETRYING        | 重试成功               | ANALYZING       |
| RETRYING        | 重试失败               | FAILED          |
| GENERATING_TEST | 生成成功               | WRITING_BACK    |
| GENERATING_TEST | 生成失败               | PARTIAL_SUCCESS |
| GENERATING_TEST | 用户取消               | CANCELLED       |
| WRITING_BACK    | 回写成功               | COMPLETED       |
| WRITING_BACK    | 回写失败               | PARTIAL_SUCCESS |
| WRITING_BACK    | 超时                   | TIMEOUT         |
| TIMEOUT         | 自动重试               | RETRYING        |
| TIMEOUT         | 重试超限               | FAILED          |
| PARTIAL_SUCCESS | 人工重试回写           | WRITING_BACK    |
| DEGRADED        | 人工重试               | ANALYZING       |

**受控回退**（仅允许以下三条，须记录审计日志并累加重试次数）：`TIMEOUT → RETRYING`、`PARTIAL_SUCCESS → WRITING_BACK`、
`DEGRADED → ANALYZING`。禁止主状态在 2/3/4 之间互转，禁止回退至 0-待处理。

**主状态 ↔ 业务状态映射**：

| 主状态   | 业务状态                                                    |
|:---------|:------------------------------------------------------------|
| 0 待处理 | RECEIVED、PARSING、QUEUED                                   |
| 1 处理中 | ANALYZING、GENERATING_TEST、WRITING_BACK、RETRYING、TIMEOUT |
| 2 已完成 | COMPLETED、PARTIAL_SUCCESS、DEGRADED                        |
| 3 失败   | FAILED                                                      |
| 4 已取消 | CANCELLED、SKIPPED_QUOTA                                    |

### 4.3 Webhook 接收响应策略（来自 SRS FR-022）

| 场景       | HTTP 状态 | 说明                         |
|:-----------|:----------|:-----------------------------|
| 处理成功   | 200 OK    | 校验通过，任务已入队         |
| 签名错误   | 401       | 安全拦截，不重试             |
| 非目标事件 | 200 OK    | 如 Push 事件，直接忽略       |
| 重复请求   | 200 OK    | 幂等性拦截                   |
| 参数错误   | 400       | 数据格式不对，重试无效       |
| 系统繁忙   | 503       | MQ 满/系统过载，触发平台重试 |

### 4.4 智能分析引擎三阶段流水线（BR-01~BR-10）

- **阶段一 变更意图分析**：输出变更摘要、影响范围、隐含需求点。
- **阶段二 评审意见生成**：基于阶段一上下文，按规则维度生成评审意见。
- **阶段三 测试用例生成**：与阶段二并行，各自独立调用 LLM；可插拔，可关闭。

关键规则：Token 预算熔断（默认 8000，超出截断或降级）、结果缓存（同一 commit 变更意图缓存
24h）、降级策略（主模型不可用切换备用模型）、并发控制（同仓库串行、跨仓库并行，分布式锁）、超时重试（默认 60s，最多 3 次，间隔
5s/30s/120s）。

### 4.5 大变更处理策略（FR-025）

- **硬性阈值拦截**：单文件 >1000 行跳过评审；单次 MR 总变更 >2000 行触发精简模式（仅评审前 10 个核心文件）；文件数 >20
  触发目录级评审；Payload >5MB 拒绝请求（HTTP 413）。
- **智能精简**：上下文折叠、非代码内容过滤、主语言识别。
- **降级模式**（触发条件中的 Token 指 **整任务输入 Token 估算值（含阶段一）**，估算方法与判定口径见《Prompt（指令）设计说明书》§5.2 / §5.5）：

| 模式     | 触发条件        | 行为                                              |
|:---------|:----------------|:--------------------------------------------------|
| 标准模式 | Token < 4k      | 全量分析                                          |
| 精简模式 | 4k ≤ Token ≤ 8k | 变更意图 + 关键逻辑评审，跳过风格检查，不生成测试 |
| 速览模式 | Token > 8k      | 仅安全检查（SQL 注入/硬编码密码/空指针）          |
| 分片模式 | 单文件极大      | 多 Chunk 并行评审（建议二期实现）                 |

### 4.6 反馈闭环与模型优化（FR-026）

- 误报特征库（BR-FB-01）：标记误报时提取 AST 特征与语义向量入库。
- 动态上下文注入（BR-FB-02）：相似度 >85% 时注入负面约束示例。
- 确认样本库（BR-FB-03）：确认有效且提交修复后存入高质量修复样本库供 Few-shot。
- 效果评估报表（BR-FB-04）：每周生成模型效果周报。

### 4.7 成本管理流程（FR-021）

- 实时计费（BR-COST-01）：每次 LLM 调用后按 Input/Output Token 及单价更新消耗。
- 阈值告警（BR-COST-02）：达 80%/90% 配额时告警。
- 熔断机制（BR-COST-03）：达 100% 配额暂停该范围 AI 评审，任务置 `SKIPPED_QUOTA`，MR 留言提示。
- 配额重置（BR-COST-04）：支持按月/周自动重置或手动调整。

## 5 数据设计概要

依据 SRS 第 6 章"数据需求"，系统核心数据实体如下（数据库 PostgreSQL 18+，JSONB 用于场景偏好/审计详情等半结构化数据）。

### 5.1 实体关系概览

物理模型共 **26 张表**（PostgreSQL 18+，JSONB 用于场景偏好/审计详情等半结构化数据），本节为概览，**字段级定义以《LLD》§4 为准**（与 SRS 第 6 章字段语义一致，LLD 增补了外键与冗余列）：

| 分类       | 实体表                                                                                                                   |
|:-----------|:-------------------------------------------------------------------------------------------------------------------------|
| 权限与组织 | `sys_user`、`sys_role`、`sys_user_role`、`sys_dept`、`sys_menu`、`sys_role_menu`、`sys_user_platform`、`data_permission` |
| 项目与仓库 | `project`、`repo`                                                                                                        |
| 评审核心   | `review_task`、`review_change_analysis`、`review_comment`、`test_case`                                                   |
| 规则与指令 | `prompt_template`、`prompt_version`、`review_rule`、`test_strategy`                                                      |
| 接入与配置 | `platform_config`、`model_config`、`notification_config`                                                                 |
| 运维与成本 | `audit_log`、`cost_quota`、`cost_consumption`                                                                            |
| 反馈闭环   | `false_positive_feature`、`fix_sample`                                                                                   |

### 5.2 关键实体说明

- **评审任务表（`review_task`）**：主状态 `status`（0-4）、业务状态 `sub_status`（14 态唯一口径）、综合评分 `score`、是否含测试用例
  `has_test_cases`、触发方式 `triggered_by`（0-Webhook/1-手动）、降级模式 `fallback_mode`
  （STANDARD/STREAMLINED/QUICK_SCAN/SHARDED）。
- **评审意见表（`review_comment`）**
  ：关联任务、文件路径/行号、维度（BUG/PERFORMANCE/SECURITY/STYLE/READABILITY）、严重等级（BLOCKER/CRITICAL/MINOR）、确认状态
  `confirm_status`（0-待确认/1-有效/2-误报）。
- **测试用例表（`test_case`）**：覆盖场景（POSITIVE/BOUNDARY/EXCEPTION）、来源 `source`（0-AI/1-手动）、验证状态 `verify_status`
  （0-待验证/1-通过/2-失败）。
- **指令模板表（`prompt_template`）**：分类（SYSTEM/REVIEW/TEST_GEN/COMMON）、支持变量占位符；版本历史存于 `prompt_version`
  ，支持对比与回滚。
- **评审规则表（`review_rule`）**：所属维度、严重等级、关联指令模板 `prompt_template`，系统内置不可删除。
- **测试策略表（`test_strategy`）**：策略名称、目标框架、场景偏好（JSONB）、命名规范、代码风格模板、指令模板、是否全局默认（`is_default`）。
- **平台接入表（`platform_config`）**：Access Token 与 Webhook Secret，Token 加密存储。
- **模型配置表（`model_config`）**：提供商、模型、API 地址/Key（AES-256 加密）、温度、max_tokens、超时（默认 60s）、单价（input/output
  price）、适用场景（REVIEW/TEST_GEN）。
- **成本表**：`cost_quota`（配额规则，含周期/上限/告警阈值/重置方式）、`cost_consumption`（按主体+日期+模型聚合 Token 与金额，由
  BR-COST-01 实时更新）。
- **审计日志表（`audit_log`）**：操作人、类型、对象、详情（JSONB）、IP、时间；保留 180 天。
- **数据权限表（`data_permission`）**：主体（ROLE/DEPT）× 资源（REVIEW_TASK/DASHBOARD/RULE）× 范围（ALL/DEPT_AND_SUB/SELF）；为**可配置表格驱动**模型，内置角色策略仅作兜底（LLD §7.2）。
- **项目表与仓库表（`project`、`repo`）**：`project` 承接成本归集与配额主体（BR-COST-01/03）；`repo` 登记已接入仓库，承载 `test_strategy_id`（FR-010）与 `is_secret`（涉密仓库合规约束，见《Prompt 设计说明书》§11.2）。
- **变更意图分析表（`review_change_analysis`）**：阶段一的结构化输出（摘要/影响文件/隐含需求/风险点），支撑 FR-006 Tab1 与结果缓存（BR-05）。
- **反馈闭环表（`false_positive_feature`、`fix_sample`）**：分别承载 BR-FB-01 误报特征库与 BR-FB-03 高质量修复样本库。
- **菜单与平台账号（`sys_menu`、`sys_role_menu`、`sys_user_platform`）**：控制台动态菜单（前端设计说明书 §4.1）与 MR 提交者到系统用户的映射（LLD §4.26 作者解析策略）。
- **通知配置表（`notification_config`）**：渠道、加签密钥与触发条件，支撑 FR-020。

> 完整字段定义（类型、约束、说明）以《LLD》§4「数据库详细设计」为准，字段语义依据 SRS 第 6 章。

|:---------|:-----------------------------------------------------------------|

### 7.1 性能需求（SRS 4.1）

| 指标                  | 要求                                 |

### 7.2 安全需求（SRS 4.2）

| 维度         | 要求                                                                                                                                                                                          |
|:-------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 身份认证     | JWT Token，有效期 7 天，支持 Refresh Token 续期                                                                                                                                               |
| 密码存储     | BCrypt 加密，不可逆                                                                                                                                                                           |
| API 鉴权     | 所有接口校验 Token + 角色权限                                                                                                                                                                 |
| 敏感数据     | Access Token、API Key 使用 AES-256 加密存储                                                                                                                                                   |
| 传输安全     | 全站 HTTPS；与 LLM 通信强制 HTTPS/TLS 1.2+                                                                                                                                                    |
| 防重放       | 分平台实施：GitHub / Gitea 校验 HMAC 签名并附加 **±300s 时间窗**（超出窗口的请求直接拒绝）；GitLab 不提供时间戳，由 Token 比对 + IP 黑名单 + 幂等键共同防重放（SRS §4.2 / BR-W-06 / BR-W-07） |
| SQL 注入防护 | 参数化查询，禁止拼接 SQL                                                                                                                                                                      |
| XSS 防护     | 前端输入输出转义，CSP 策略                                                                                                                                                                    |
| 代码数据脱敏 | 发送 LLM 前正则扫描 Diff，敏感字段替换为 `***REDACTED***`                                                                                                                                     |
| 隐私合规     | 标识 LLM 是否开启"数据训练"；核心涉密项目强制私有化部署或承诺不保留数据的商业模型                                                                                                             |

Webhook 签名验证按平台区分（GitLab `X-Gitlab-Token` 直接比对；GitHub/Gitea `X-Hub-Signature-256`/`X-Gitea-Signature` 用
HMAC-SHA256，并附加 **±300s 时间窗**，超出窗口的请求直接拒绝；GitLab 侧无时间戳可用，依赖 Token 比对 + IP 黑名单 + 幂等键实现防重放）；连续 5 次签名失败 IP 自动加入临时黑名单（封禁 30 分钟）。

### 7.3 可靠性需求（SRS 4.3）

### 8.2 部署架构要点

- **无状态后端**：Spring Boot 应用多实例部署，前置负载均衡，满足 ≥50 QPS 并发与水平扩展要求（4.5）。
- **异步处理**：Webhook 接收服务与后台分析 Worker 通过 Kafka 解耦，Worker 可独立横向扩容以应对 LLM 处理耗时。
- **存储与缓存**：PostgreSQL 主库 + Redis（幂等键缓存 24h、结果缓存 24h、分布式锁）；二者均需满足备份与高可用要求。
- **外部依赖**：代码托管平台需开启 Webhook 且网络可达；LLM 服务商 API 可用性 ≥ 99.5%；企业内部网络允许访问 LLM 端点（SRS 2.6
  假设与依赖）。

#### 8.2.1 部署单元拓扑（含 Worker）

平台由三个独立可执行单元组成，与 §2.4.6 一一对应，通过 Kafka 解耦、共享存储：

```
                         ┌────────────────────────────────────────┐
                         │           负载均衡 (LB)                │
                         └──────┬───────────────────┬─────────────┘
                                │                   │
                  RPC (Bearer)  │           Webhook (HMAC 签名)
                                │                   │
                  ┌─────────────▼────────┐  ┌───────▼────────┐
                  │     aicr-web         │  │  aicr-webhook  │
                  │  控制台 RPC 入口     │  │ 接收/签名/幂等 │
                  │ service+sec+api+base │  │ 入队 Kafka     │
                  └─────────────┬────────┘  └─────────┬──────┘
                                │                     │
                                │     ┌───────────────▼──────┐
                                │     │   Kafka 队列         │
                                │     │ TOPIC_REVIEW_REQUEST │
                                │     └─────────────┬────────┘
                                │                   │ 消费
                                │         ┌─────────▼────────┐
                                │         │  aicr-worker     │
                                │         │ 驱动 engine 执行 │
                                │         │ 分析/回写/反馈   │
                                │         └─────────┬────────┘
                                │                   │
                  ┌─────────────▼──────┐  ┌─────────▼──────────┐
                  │   PostgreSQL 18+   │  │   Redis 8.0+       │
                  │ (Flyway 由 worker  │  │ 幂等/缓存/分布式锁 │
                  │  单一单元执行)     │  └────────────────────┘
                  └────────────────────┘
        外部集成：代码托管平台 / LLM 提供商 / 通知渠道（经 engine 出站）
```

- `aicr-web`：控制台 RPC 入口，前置负载均衡，按在线用户/QPS 横向扩容。
- `aicr-webhook`：独立部署、独立扩容，保障 ≥50 QPS 下 P99 ≤200ms（HLD 7.1）。
- `aicr-worker`：Kafka 消费入口，装配并驱动 `engine` 执行；按消费 lag 横向扩容，隔离 LLM 长任务对控制台 API 线程池/连接池的影响（满足 LLD 9.1 首屏 ≤2s、API P99 ≤2s）。
- 三单元共享 PostgreSQL/Redis/Kafka；数据库迁移（Flyway/Liquibase）仅由 `worker` 单一单元执行，避免多实例并发上锁。

### 8.3 可用性、备份与恢复

- 系统可用性目标 ≥ 99.9%（4.3）。
- 数据库每日全量备份 + 实时 WAL 连续归档，支持 PITR。
- 故障恢复目标：RTO ≤ 30 分钟，RPO ≤ 5 分钟。

### 8.4 环境依赖假设（SRS 2.6）

- 代码托管平台已开启 Webhook 功能且网络可达。
- LLM 服务商 API 可用性 ≥ 99.5%。
- 企业内部网络允许平台访问 LLM API 端点。
