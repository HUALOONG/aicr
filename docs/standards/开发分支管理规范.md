## 1 总则

### 1.1 目的

规范 `aicr` 项目的分支模型、合并规则与版本节奏，保证：

1. `master` 始终处于可发布状态；
2. 架构红线（`engine↛service`、`web↛engine`、`webhook↛{service,engine}`、`common↛Spring`）在合并前被拦截，而非集成后才暴露；
3. Flyway 迁移脚本、接口契约与实现在同一变更单元内对齐，避免文档/契约与代码脱节。

### 1.2 适用范围

- 代码：9 个 Maven 模块（`aicr-common`/`api`/`security`/`base`/`service`/`engine`/`web`/`webhook`/`worker`）与前端工程 `aicr-console`；
- 文档：`SRS` / `HLD` / `LLD` / `Prompt（指令）设计说明书` / `前端详细设计说明书` / `开发分支管理规范`；
- 契约：`../api/openapi.yaml`、Flyway 迁移脚本 `V*.sql`。

### 1.3 基本原则

- **文档、契约、代码同分支同 PR**，禁止"先合契约后补实现"或"文档另行维护"；
- **分支按纵向需求切片，不按 Maven 模块切长期分支**（一个 FR 通常横跨多个模块）；
- **特性分支短命**：生命周期 ≤ 3 个工作日，超出应拆分为多个分支或引入开关。

## 2 分支模型

### 2.1 模型总览

采用 **`master` + `develop` 双主干 + 短特性分支 + 发布冻结分支**（精简 GitFlow）：

```
master   ──●───────────────●──────────────────●──────────────▶  发布线（始终可发布）
             ↑(tag v0.1.0)   ↑(tag v0.2.0)      ↑(tag v1.0.0)
develop  ─●──●──●──●──●──●──●──●──●──●──●──●──●──●──────────▶  集成线（最新已集成成果）
           ↑  ↑  ↑
      feature/* fix/* docs/*

release/v1.0.0                    ●──●──●──(冻结修 bug)──┐
                                                          ↓
                                                       master + develop
```

- `master`：**发布线**。每一次合并都对应一个可发布版本，并在合并后打 tag。
- `develop`：**集成线**。所有特性分支的唯一汇入点，代表"下一个版本的当前状态"。
- `release/*`：**冻结线**。仅 `v1.0.0` 正式发布前创建；内部版本 v0.1~v0.6 直接从 `develop` 验收后合并到 `master`，不单独开 release 分支。

### 2.2 分支清单

| 类型         | 命名示例                                               | 来源 → 合回                                | 生命周期 | 保护级别                                    |
|:-------------|:-------------------------------------------------------|:-------------------------------------------|:---------|:--------------------------------------------|
| 主干（发布） | `master`                                               | `develop` / `release/*` / `hotfix/*` → —   | 永久     | 禁 push，禁 force push，需 PR + CI + Review |
| 主干（集成） | `develop`                                              | `feature/*` `fix/*` `docs/*` `chore/*` → — | 永久     | 禁 push，禁 force push，需 PR + CI          |
| 特性         | `feature/FR-023-dimension-batch`                       | `develop` → `develop`                      | ≤3 天    | 无（单人开发可 force push）                 |
| 缺陷         | `fix/FR-005-dept-scope-filter`                         | `develop` → `develop`                      | ≤2 天    | 无                                          |
| 热修         | `hotfix/v1.0.1-webhook-401`                            | `master` → `master` + 回灌 `develop`       | ≤1 天    | 需 PR + CI                                  |
| 发布冻结     | `release/v1.0.0`                                       | `develop` → `master` + 回灌 `develop`      | 冻结期   | 禁 push，仅收 bugfix                        |
| 文档/杂项    | `docs/srs-status-caliber`、`chore/init-maven-skeleton` | `develop` → `develop`                      | 短       | 无                                          |

### 2.3 命名规范

```
<type>/<需求编号>-<小写英文短横线简述>
```

- `type`：`feature` / `fix` / `hotfix` / `release` / `docs` / `chore` / `refactor` / `test`；
- 需求编号优先使用 `FR-xxx`；无对应 FR 时（如纯工程改动）可省略，改为 `chore/enforcer-archunit`；
- 简述用小写英文 + 连字符，≤ 4 个词，不写中文。

## 3 日常开发流程

### 3.1 特性开发

```bash
git switch develop && git pull
git switch -c feature/FR-023-dimension-batch
# 开发 + 自测：mvn verify（含 Enforcer + ArchUnit）、前端 vp check
git push -u origin feature/FR-023-dimension-batch
# 提 PR → develop，CI 全绿 + 至少 1 人 Review 后 squash merge
```

要点：

1. 分支自 `develop` 切出，**不直接切自 `master`**；
2. 开发期间每日 `git fetch origin develop && git rebase origin/develop`，避免分叉积累；
3. 单一 PR 只做一件事，跨模块改动（`common` → `api` → `service` → `engine` → `web`）**允许且鼓励**放在同一分支，只要它服务于同一个 FR。

### 3.2 合并方式

| 合并路径                           | 方式             | 理由                               |
|:-----------------------------------|:-----------------|:-----------------------------------|
| `feature/*` → `develop`            | **squash merge** | 保持集成线线性、便于整体 revert    |
| `develop` → `master`               | **merge commit** | 保留版本合并记录，便于追溯每个 tag |
| `release/*` → `master` / `develop` | merge commit     | 保留冻结期修复记录                 |
| `hotfix/*` → `master`              | squash merge     | 紧急修复保持简洁                   |

## 4 版本与里程碑

### 4.1 版本号规则

语义化版本 `MAJOR.MINOR.PATCH`；三个可执行 jar 与前端共用同一版本号，由父 POM 的 `revision` 统一定义，禁止各单元单独发版。

### 4.2 内部版本规划（v0.1 ~ v0.6 → v1.0.0）

| 版本       | 里程碑                | 覆盖范围                                                                        | 可验收标准（DoD）                                                                             |
|:-----------|:----------------------|:--------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------|
| **v0.1**   | M1 权限与配置         | FR-014~017（用户/角色/部门/数据权限）、FR-018~020（平台接入/模型配置/通知设置） | 可登录并获取菜单；可配置平台与模型并通过连通性测试；数据权限过滤生效                          |
| **v0.2**   | M2 核心引擎           | FR-022~026 + Kafka 消息契约（LLD §10）                                          | 推送 MR/PR 后能收到 Inline Comment 与 Summary Comment；大变更触发降级；状态机流转与 §6.2 一致 |
| **v0.3**   | M3 智能分析 + 概览    | FR-001~007                                                                      | 概览四图出数；任务列表 14 态筛选；报告三 Tab 与 Diff 视图可用；变更追溯图谱可渲染             |
| **v0.4**   | M4 规则配置           | FR-008~011 + `PromptRenderEngine`                                               | 指令版本化/回滚可用；规则快照与维度分桶评审生效；测试策略可绑定仓库                           |
| **v0.5**   | M5 成本 + 运维 + 反馈 | FR-012/013、FR-021、FR-026                                                      | 配额告警与熔断（四档状态）生效；审计日志留存；误报/确认反馈进入特征库与样本库                 |
| **v0.6**   | M6 前端全量联调       | 21 个页面 + 非功能指标                                                          | 首屏 ≤2s、API P99 ≤2s；Webhook P99 ≤200ms 且 ≥50 QPS；单测覆盖 ≥80%                           |
| **v1.0.0** | 正式发布              | 全量 + 冻结修复                                                                 | 由 `release/v1.0.0` 冻结并回归通过后发布                                                      |

### 4.3 内部版本发布流程（v0.1 ~ v0.6）

```bash
# 1. develop 上完成里程碑并通过验收
# 2. 提 PR：develop → master（全量 CI + 冒烟 + 至少 1 人 Review）
# 3. 合并后在 master 上打 tag
git switch master && git pull
git tag -a v0.1.0 -m "v0.1.0 M1 权限与配置"
git push origin v0.1.0
# 4. 产出制品：aicr-web / aicr-webhook / aicr-worker 三个 jar + 前端 dist/
```

### 4.4 正式版本发布流程（v1.0.0）

```bash
git switch develop && git pull
git switch -c release/v1.0.0
# 冻结期：仅合入 bugfix（fix/* → release/v1.0.0），并同步回灌 develop
# 回归通过后：
#   ① release/v1.0.0 → master，打 tag v1.0.0
#   ② master → develop（保证 develop 含全部修复）
```

### 4.5 热修流程

```bash
git switch master && git pull
git switch -c hotfix/v1.0.1-webhook-401
# 修复 → PR → master → tag v1.0.1
# 同步回灌 develop（若存在 release 分支则一并回灌）
```

**二期项不入 v1.0**：多租户 `tenant_id`、`AUDITOR`/`OPERATOR` 角色、Gitea 事件幂等键、指令灰度发布、大变更分片模式（SHARDED）均为二期，禁止混进 v1.0 分支；相关代码如需预留扩展点，应在 PR 描述中显式说明。

## 5 CI 门禁矩阵

| 触发场景       | 必跑项                                                                                                               | 阻断条件         |
|:---------------|:---------------------------------------------------------------------------------------------------------------------|:-----------------|
| PR → `develop` | `mvn verify`（含 Maven Enforcer + ArchUnit）、后端单测、前端 `vp check`、`vp test --run`、`openapi.yaml` schema 校验 | 任一失败阻断合并 |
| PR → `master`  | 上述全部 + Flyway 脚本幂等校验 + 契约快照比对 + 冒烟                                                                 | 任一失败阻断     |
| 合入 `develop` | 全量构建，推送快照制品                                                                                               | 构建失败告警     |
| `tag v*`       | 产出三个可执行 jar + 前端 `dist/`                                                                                    | —                |

**红线拦截位置**：Maven Enforcer 负责模块级禁止依赖（`LLD` 附录 C.1），ArchUnit `ArchitectureTest` 负责分层校验（`LLD` 附录 C.2）。两者均在 `mvn verify` 阶段执行，因此 **PR 未跑 `mvn verify` 即视为未完成自检**。

## 6 关键约定

### 6.1 数据库变更规范（Flyway 迁移）

所有数据库结构/数据变更一律通过 Flyway 迁移脚本完成，**禁止**在生产库手工执行 DDL/DML；紧急修复须经 DBA 与负责人双审批，并回填补偿脚本。仅 `aicr-worker` 启动时执行迁移（`HLD` §2.4.6 / `DBD` §7），其余服务 Flyway 关闭，避免多实例并发上锁。

**单一执行单元**：脚本目录固定为 `aicr-worker/src/main/resources/db/migration`，由 `worker` 加载（`spring.flyway.enabled=true`）；`web` / `webhook` 一律 `enabled=false`。多实例部署时由 Flyway 内置锁保证唯一执行，但建议仍保持单一 `worker` 实例策略。

**命名规范**（必守）：

- 基线：`V1__init.sql`；
- 增量：`V{yyyyMMdd}_{两位序号}__{简述}.sql`（如 `V20260912_01__add_repo_is_secret.sql`），按版本号升序执行；避免多人抢占 `V2__` 之类低位版本号。

**变更纪律**：

- 脚本与对应代码必须**在同一 PR** 内提交（CI 门禁校验，见 §8 检查清单）；
- 合入前检查 `develop` 上已有最大版本号，冲突则在 PR 中显式说明并重新编号；
- **禁止修改已发布脚本**（会导致校验和失败）；结构性变更一律新增更高版本脚本；字段语义变更须同步 `../api/openapi.yaml`、LLD 字段说明与列注释，并升版本；
- 破坏性行为（删列、改类型、改列语义）须评估数据迁移与回滚方案，并在 PR 说明。

**幂等要求**：数据型迁移须 `WHERE NOT EXISTS` / `IF NOT EXISTS`；种子显式 ID 后须 `setval` 重置序列；`INSERT` 种子须可重复执行。

**环境与密钥**：开发种子（V1 明文占位 key）仅限本地；生产密钥由管理端界面写入 AES-256 密文，**迁移脚本不得出现真实密钥明文**；时间统一 `TIMESTAMPTZ`（UTC 存储）。

**回滚**：Flyway 不自动回滚；破坏性变更须配对提供补偿脚本（更高版本）或经 DBA 执行备份恢复（备份策略见 `DBD` §9.1：`pg_dump` + WAL 归档）。

> 脚本清单、对象注释规范与字段级语义以 `DBD` §7 / §4 为事实依据；本节约为研发协作与 CI 门禁的统一约束。

### 6.2 接口契约与文档

- `../api/openapi.yaml` 是字段级唯一事实依据（98 个接口），**契约变更必须与后端 DTO/Controller 在同一 PR**；
- 前端 `src/api/types/` 为生成产物（只读），不参与人工评审；
- SRS/HLD/LLD/Prompt/前端说明书的修订与代码同分支，避免"文档说一套、主干另一套"；
- 状态口径（`sub_status` 14 态）、错误码、降级阈值等跨文档口径，修改时必须同步所有引用处。

### 6.3 环境与配置

- **不用分支区分环境**：dev/test/prod 差异一律通过配置文件或配置中心注入（`SRS` §4.4），禁止出现 `feature/xxx-test-env` 这类分支；
- 三个部署单元共享同一 PostgreSQL / Redis / Kafka（`HLD` §2.4.6），连接信息不进代码库。

## 7 提交信息规范

采用 Conventional Commits，并在正文/尾注关联需求编号：

```
<type>(<scope>): <中文简述> (<需求编号>)

feat(engine): 阶段二改为按维度分桶批量调用 (FR-023)
fix(webhook): 业务去重窗口内旧任务取消与新任务同事务 (BR-W-08)
docs(srs): 统一 sub_status 筛选口径
refactor(service): 数据权限改为 data_permission 表驱动 (FR-017)
chore(ci): PR 增加 ArchUnit 与 Enforcer 门禁
```

- `type`：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`；
- `scope`：Maven 模块名（`common`/`api`/`security`/`base`/`service`/`engine`/`web`/`webhook`/`worker`/`console`）或 `ci`/`db`；
- 一行不超过 72 字符；正文说明"为什么改"，不重复 diff 内容。

## 8 PR 检查清单

提交 PR 时逐项确认（建议作为 PR 模板固化）：

- [ ] 标题含 `<type>(<scope>)` 与需求编号（FR / BR）
- [ ] 本地已通过 `mvn verify`（**含 Enforcer 与 ArchUnit**）
- [ ] 前端改动已通过 `vp check` 与 `vp test --run`
- [ ] 新增/修改的单元测试覆盖本次逻辑，整体覆盖率不降低（≥80%）
- [ ] **如含 Flyway 脚本**：已与 `develop` 现有最大版本号比对，无冲突；脚本与代码同 PR
- [ ] **如改接口**：`../api/openapi.yaml` 已同步，字段与 `Param`/`Data` schema 一致
- [ ] **如改状态/阈值/错误码/枚举**：SRS、HLD、LLD、Prompt、前端说明书已同步
- [ ] 未引入二期范围内容（多租户、预留角色、Gitea 幂等键、灰度、SHARDED）
- [ ] 未提交密钥、Token 等敏感信息（凭据一律走配置或配置中心）

## 9 分支保护配置建议

| 分支                    | 禁止直接 push | 禁止 force push | 必需 PR | 必需 CI | 必需 Review | 线性历史 |
|:------------------------|:-------------:|:---------------:|:-------:|:-------:|:-----------:|:--------:|
| `master`                |      ✔       |       ✔        |   ✔    |   ✔    |    ≥1 人    |   建议   |
| `develop`               |      ✔       |       ✔        |   ✔    |   ✔    |    ≥1 人    |   建议   |
| `release/*`             |      ✔       |       ✔        |   ✔    |   ✔    |    ≥1 人    |    ✔    |
| `feature/*`、`fix/*` 等 |       —       |        —        |   ✔    |   ✔    |    ≥1 人    |    —     |

> 若使用 GitLab，对应能力为 Protected Branches + Merge Request Approvals；
> 
> 若使用 GitHub，对应 Branch protection rules。
> 
> 二者配置等价，CI 模板见各自平台的流水线文件。
